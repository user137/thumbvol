# DECISIONS.md

Архітектурні рішення й відкинуті альтернативи, з причиною. Це джерело істини для "чому", коли
воно розходиться з CLAUDE.md (поточний стан) чи TASKS.md (беклог).

## D1 — Linux: без ексклюзивного grab пристрою в v1

**Рішення:** `platform::linux` читає `/dev/input/eventN` неексклюзивно (без `EVIOCGRAB`), тому
бічний скрол миші й далі доходить до фокусної програми (`REL_HWHEEL` не проковтується), на
відміну від Windows, де хук глушить `WM_MOUSEHWHEEL` повністю.

**Причина:** MX Master репортує кліки, вертикальний скрол і бічне колесо через один evdev-вузол.
Ексклюзивний grab цього вузла вбив би всю мишу для решти системи (курсор, кліки), не лише бічне
колесо — неприйнятно для миші, якою користуються постійно.

**Відкинута альтернатива:** grab оригінального пристрою + створення virtual-passthrough-пристрою
через uinput, що ретранслює все, крім `REL_HWHEEL` (класичний патерн `evsieve`/
`interception-tools`). Технічно правильне рішення для повної паритетності з Windows, але суттєво
більше коду й поверхні для помилок — відкладено, не потрібне для v1 (див. kickoff-відповідь:
"тільки гучність, мінімальний обсяг"). Кандидат на TASKS.md, якщо side-scroll в апках виявиться
реальною проблемою на практиці.

## D2 — Гучність через синтетичні медіа-клавіші, не через audio API напряму

**Рішення:** Windows — `SendInput(VK_VOLUME_UP/DOWN)`; Linux — віртуальна uinput-клавіатура,
`KEY_VOLUMEUP/KEY_VOLUMEDOWN`. Жодного прямого виклику Core Audio (`IAudioEndpointVolume`) чи
PulseAudio/PipeWire client API.

**Причина:**
1. Нативний OSD гучності ОС з'являється безкоштовно — і Windows, і більшість Linux DE вже
   реагують на ці клавіші так само, як на фізичну мультимедійну клавіатуру.
2. Одна точка інтеграції на Linux незалежно від того, PulseAudio чи PipeWire під капотом —
   working через DE-рівень keybinding, а не проти конкретного sound-сервера.
3. Мінімум коду/залежностей (жодного нового audio-крейту).

**Компроміс:** якщо DE користувача не має стандартного біндингу цих клавіш (рідкісний tiling-WM
без DE), гучність не зміниться — задокументовано в README як відома межа.

## D3 — Два окремих числа: `notches_per_step` і `sensitivity`

**Рішення:** `notches_per_step` (скільки фізичних кліків колеса на один крок гучності, дільник) і
`sensitivity` (скільки натискань клавіші гучності на один такий крок, множник) — окремі поля, не
одне число з плаваючою комою.

**Причина:** `WheelAccumulator` тримає точний цілочисельний рахунок нотчів без дрейфу (важливо,
бо стан накопичується між викликами `feed()`). Множник — ортогональна, окремо обмежена
(`MAX_STEPS_PER_FEED`) вісь, яку не можна змішувати з рахунком нотчів без ризику втратити точність
накопичення.

## D4 — Конфіг ігнорує невідомі ключі (permissive parsing)

**Рішення:** `Config` не використовує `#[serde(deny_unknown_fields)]`.

**Причина:** kickoff-відповідь зафіксувала "тільки гучність зараз, але з архітектурою під
розширення" — майбутні секції (інші кнопки/жести) не повинні ламати парсинг старого конфіг-файлу
при апдейті бінарника. Плата: одруківка в ключі мовчки ігнорується, а не падає з помилкою —
прийнятно для персонального, не мультитенантного інструменту.

## D5 — Автовизначення Linux-пристрою за здатністю `REL_HWHEEL`, не за VID/PID

**Рішення:** `platform::linux::find_wheel_device` шукає перший evdev-пристрій, що підтримує
`REL_HWHEEL`, замість матчингу на Logitech vendor ID.

**Причина:** працює з будь-якою мишею з бічним колесом, не лише Logitech — і не потребує
підтримки таблиці PID для кожної моделі MX Master. Explicit override — `[linux] device_path` у
конфізі — для мультимишевих сетапів чи хибного автовизначення.

## D6 — Назва пакета `thumbvol`, не `logi-*`

**Рішення:** крейт/бінарник називається `thumbvol`.

**Причина:** це неофіційний сторонній інструмент, не продукт Logitech — уникнення торгової марки
в назві опублікованого пакета/бінарника.

## D7 — Іконка трею: власний глиф "бічне колесо", не літера бренду

**Рішення:** іконка трею — стилізоване бічне колесо зі стрілками вгору/вниз (намальовано
програмно через .NET `System.Drawing`, `assets/tray.ico`, вбудовано через `embed-resource` +
`assets/tray.rc`), не літера "L".

**Причина:** користувач спершу попросив літеру "L" (натяк на "Logi"), але це створює реальний
ризик бренд-плутанини — стороння програма з іконкою, що натякає на офіційний продукт Logitech,
може ввести в оману будь-кого, хто її встановить, і суперечить D6 вище (уникати торгової марки). Запропонована альтернатива — глиф, що прямо зображує функцію застосунку
(бічне колесо), без будь-якої асоціації з чужим брендом — прийнята користувачем.

## D8 — Тільки Windows має трей/меню-налаштування в v1

**Рішення:** трей-іконка, меню (Reload/About/Exit, підменю Sensitivity, чекбокс Invert) і
live-редагування конфігу з диска реалізовані лише в `platform::windows`. Linux — досі лише
конфіг-файл, без UI.

**Причина:** трей-протокол на Linux не єдиний (StatusNotifierItem/AppIndicator залежить від DE,
частина сучасних DE — зокрема GNOME без розширень — взагалі не показує класичний трей), тож
"один код для обох ОС" тут неможливий без окремої, суттєво важчої абстракції. Windows-реалізація
вже вирішує запит користувача ("не бачитиму наявність процесу") на платформі, де зараз ведеться
розробка й тестування наживо; Linux-паритет — кандидат на майбутнє, залежно від того, наскільки
це виявиться потрібним на практиці (див. TASKS.md).

## D9 — Live-редагування конфігу (invert/sensitivity) читає й пише реальний файл, не тільки in-memory стан

**Рішення:** зміна Invert/Sensitivity з трей-меню одразу: (1) перебудовує активний
`WheelAccumulator`, (2) серіалізує весь `Config` і перезаписує конфіг-файл на диску
(`Config::save`).

**Причина:** відповідає "install and forget" — вибір, зроблений через трей, має пережити
перезапуск процесу/перезавантаження ОС так само, як і ручна правка файлу. Альтернатива
(тримати зміну лише в пам'яті процесу) означала б, що кожен рестарт скидає користувача до
значень зі старого файлу — сюрприз, якого легко уникнути ціною одного виклику `toml::to_string_pretty`
+ `fs::write`.
